# CI и релизы OpenShield

Авторитетная документация релизного CI находится в
[`.github/README-CI.ru.md`](.github/README-CI.ru.md). Сам процесс задан в
`.github/workflows/release.yml`, а машиночитаемый контракт поддержки — в
`packaging/ci/release-matrix.json`.

Релизный граф закрыто отказывает при любом несоответствии:

```text
Validation
    -> Quality Gate
    -> 43 сборки двоичных файлов для пар семейство/архитектура
    -> 43 сборки пакетов для пар семейство/архитектура
    -> 37 установок для 19 вариантов пакетов
    -> контейнерные тесты init-систем в закреплённых образах
    -> 74 сквозных теста фаервола
    -> ограниченный smoke-тест производительности nftables/iptables
    -> запечатанный релизный кандидат и свидетельства
    -> публикация
```

Только после успеха всех 74 функциональных заданий фаервола один
ограниченный smoke-тест производительности использует тот же двоичный файл
демона из релизного артефакта `binary-tumbleweed-amd64` на единственном стенде
openSUSE Tumbleweed `linux/amd64`. Он проверяет nftables и iptables в одноразовых
пространствах имён Docker; стенд ограничен 1800 секундами, а всё
задание — 45 минутами. Результатом становятся проверенные отчёты
JSON, CSV и Markdown.
Зафиксированный релизный профиль требует успеха обоих бэкендов и
отклоняет недостоверные или насыщенные измерения. Численные относительные пороги
остаются равны 10%, а все дельты и пересечения отдельных окон сохраняются в
свидетельствах. В релизном smoke-профиле
`cpu_latency_relative_regressions_are_advisory: true` переводит только парные
регрессии CPU cgroup DUT и задержки запросов/TCP connect в диагностический режим
для общего runner. Их средние и односторонние 95%-е доверительные границы
Стьюдента по-прежнему публикуются, но сами по себе не блокируют релиз. Парное
снижение throughput или DUT PPS блокирует релиз, когда односторонняя 95%-я
нижняя доверительная граница по не менее чем трём независимым соседним steady-парам
AB/BA превышает 10%. Превышение только среднего сохраняется как наблюдение, чтобы шум общего runner не становился причиной ложного отказа. Абсолютные пределы
CPU/RSS демона и p99 задержки, достижение целевой нагрузки, достоверность и
пропускная способность всплеска остаются обязательными. Единичный всплеск не даёт доверительного
вывода, поэтому его относительные пересечения остаются наблюдениями; его абсолютные пределы пропускной способности, достоверность и безопасность остаются блокирующими.
Абсолютный предел CPU демона равен 95% одного ядра вне всплесков
(`maximum_daemon_cpu_percent_one_core`) и 150% во время всплесков
(`maximum_burst_daemon_cpu_percent_one_core`). Допуск для всплеска ограничен:
независимый валидатор проверяет применимый предел по первичным измерениям.
В production-like-профиле оба предела равны 90%. Критерии throughput/PPS,
задержки, RSS и безопасности не изменены. Drops, повторные передачи,
ошибки NFQUEUE и fail-open-поведение всегда приводят к немедленному отказу.
Независимая контрольная проба управляемой перегрузки доказывает отсутствие
fail-open: привязанный к приложению трафик Enforcing остаётся закрытым при отказе,
пока обработчик очереди недоступен. Этот релизный smoke-тест не
выполняется в workflow запроса на изменение и не является переносимым тестом
производительности или заявлением о поддержке всех архитектур.

Каждый независимый блок CI получает 1,0 секунды разогрева. Оценка времени полного
плана нагрузки для двух бэкендов равна 609,6 секунды и обязана остаться ниже явного
предела 620 секунд. Модель конечного времени жизни keep-alive использует
пуассоновскую оценку конкурирующих событий на каждом worker вместо предположения
об одновременном истечении сокетов. Она учитывает четыре пакета закрытия и три
пакета нового handshake в прежних пределах PPS и CPS; зафиксированный чистый
keep-alive-профиль сохраняет `pps = 1280` и `cps = 160` и даёт
`200,874426 операции/с`. Заданные интенсивности и численные 10%-е релизные
пороги не снижены. Только относительные пересечения CPU и задержки в
release smoke имеют диагностическую роль; production-like-профиль задаёт
`cpu_latency_relative_regressions_are_advisory: false` и сохраняет их
блокирующими.

Клиент давления использует явный барьер готовности/старта до остановки демона.
На том же canary-veth отдельная network-only конечная точка того же транспорта
обязана успешно отвечать непосредственно до и после каждого application-bound
probe из другого исполняемого файла. Насыщение ресурсов генератора, узла
давления или canary, а также ошибки сокетов либо NIC делают доказательство
недостоверным. UDP drain ACK отправляется только после подтверждения точного
непрерывного префикса последовательности потока в ограниченном окне; стенд не
предполагает упорядоченную доставку UDP.

Если демон сообщает о карантине `BlockAll`, снимки канонической ядерной политики и статус
демона обрамляют реальные негативные TCP- и UDP-пробы. Непосредственно до и после каждой из них обязан
успешно пройти реальный loopback round trip внутри canary-контейнера, чтобы неработающий удалённый сервер не был
ошибочно принят за карантин.

Для каждого бэкенда сохраняются закреплённый Docker image ID,
точная архитектура `x86_64`, `/etc/os-release` openSUSE Tumbleweed,
`uname`, SHA-256 метаданных `repo-oss` и точный отсортированный
список RPM NEVRA. Между двумя топологиями обязаны совпадать образ,
ОС, архитектура/ядро и метаданные репозитория. RPM-манифесты хранятся
раздельно: в nftables-топологии обязан присутствовать ожидаемый эксклюзивный
пакет `nftables`, а все прочие различия зависимостей остаются явными
свидетельствами и не подменяются утверждением о полном совпадении. Это делает
запуск проверяемым, но подписанный живой репозиторий Tumbleweed всё равно меняется между
запусками. Для
публикационных показателей нужны заранее собранный performance-образ,
закреплённый по digest, выделенный runner и сохранённые свидетельства; сам по
себе успех CI не означает успешный полный прогон для публикации.

Матрица времени выполнения содержит 37 закреплённых пар
дистрибутив/платформа: 16 для `amd64`, 15 для `arm64` и 6 для
`386`. Каждая строка проходит сценарии с приоритетом nftables и только
с резервным iptables. `amd64` и `arm64` выполняются на нативных
исполнителях GitHub; `linux/386` — через прямой 32-разрядный режим
совместимости ядра x86-64.

Все 43 цели двоичных файлов и 43 цели пакетов по-прежнему
собираются. Оставшиеся 24 варианта пакетов для ARMv5/6/7,
PowerPC64LE, RISC-V 64 и IBM Z имеют статус «только сборка» и соответствуют 49 из
86 объявленных пар дистрибутив/платформа. Их тракт Cross/QEMU проверяет ELF и
выполняет непривилегированный
smoke-тест `--version`, но не даёт свидетельств установки пакета или
работы фаервола. Публикация такого артефакта не означает заявления о
поддержке во время работы или на нативном оборудовании.

Каждый пакет из проверяемого набора связан со свидетельствами
установки и фаервола по имени и SHA-256; пакеты со статусом «только
сборка» имеют только свидетельства сборки и целостности артефакта. До
первого запроса к API публикации задание с правами записи независимо
сверяет тег, ревизию исходного кода, хеш матрицы, полный список файлов,
размеры, digest и `SHA256SUMS`.

ZIP-транспорт артефактов GitHub нормализует режим обычных файлов до `0644`.
Поэтому Release Evidence явно требует этот режим от загруженных транспортных
копий ELF и использует их только для сверки байтов. Источником исполняемого
режима остаётся публикуемый `tar.xz`: он должен содержать ровно демон и TUI как
обычные файлы с режимом `0755`, а их размеры и SHA-256 должны совпадать с
транспортными копиями. При сборке пакета режим `0755` задаётся явно.

Для создания релиза задайте `[workspace.package].version` в `Cargo.toml`,
зафиксируйте полное изменение и создайте на этой ревизии совпадающий тег
`vX.Y.Z`. Числовой тег `X.Y.Z` без обязательного префикса `v` доходит только
до Validation, где завершается с явным сообщением об ошибке; компиляция и
публикация для него недоступны. Восстановление уже опубликованного релиза
разрешено только через явную опцию исправления `workflow_dispatch`;
существующие файлы с другими байтами никогда не перезаписываются.
