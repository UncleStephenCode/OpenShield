# Упаковка демона для systemd

В этом каталоге находятся unit-файл systemd, декларация sysusers и
декларация tmpfiles.
Unit-файл пригоден как для предпочтительного бэкенда nftables, так и для
автоматического резервного бэкенда `iptables`/`ip6tables`.

Устанавливайте через пакетный менеджер:

| Исходный файл | Целевой путь | Режим |
| --- | --- | ---: |
| `openshield-daemon.service` | `/usr/lib/systemd/system/openshield-daemon.service` | `0644` |
| `openshield.sysusers` | `/usr/lib/sysusers.d/openshield.conf` | `0644` |
| `openshield.tmpfiles` | `/usr/lib/tmpfiles.d/openshield.conf` | `0644` |
| релизный демон | `/usr/bin/openshield-daemon` | `0755` |
| релизный TUI | `/usr/bin/openshield-tui` | `0755` |

Выполните `systemd-sysusers` и `systemd-tmpfiles --create` до старта сервиса.
Демон намеренно отказывается частично запускаться, если нельзя найти
обязательную группу `openshield`.

## Зависимости RPM для фаервола и среды выполнения

Каждый RPM объявляет составную зависимость `(nftables or iptables)` и
рекомендует `nftables`. Поэтому обычный решатель зависимостей
устанавливает предпочтительный интерфейс nftables, но установка только с
iptables остаётся корректной, если nftables недоступен или рекомендации
отключены. Во время работы OpenShield по-прежнему сначала выбирает
nftables и использует `iptables`/`ip6tables` только как резервный бэкенд.

Каждый RPM также требует `/usr/bin/systemd-tmpfiles`. Зависимость от пути
позволяет дистрибутиву выбрать свой штатный пакет, включая
`systemd-mini`, где он доступен, и гарантирует, что послеустановочный
сценарий создаст и перемаркирует точные рабочие пути до первого
ручного запуска.

Двоичные файлы во всех RPM релизной матрицы должны быть скомпонованы статически
и не должны содержать ELF-сегмент `PT_INTERP`. Эту границу для всех целей
проверяет ELF-этап сборки; тесты установки пакета повторно подтверждают её для
проверяемых вариантов `amd64`, `arm64` и `386`. Остальные архитектуры имеют статус
«только сборка» и не имеют свидетельства установки пакета. Статическая компоновка не
отменяет ограничения совместимости с версией ядра Linux и пользовательской средой,
зафиксированные в релизных свидетельствах.

## Объекты во время работы

Сервис создаёт или проверяет:

- `/run/openshield`, заранее создаваемый tmpfiles как `root:root` с режимом `0755`;
- `/var/lib/openshield`, заранее создаваемый tmpfiles как `root:root` с режимом `0700`;
- `/run/openshield/control.sock`, владелец UID 0, режим `0600` — для изменений
  от UID 0 (группа при таком режиме намеренно не влияет на доступ);
- `/run/openshield/observe.sock`, `root:openshield`, `0660` — для
  мониторинга только для чтения от root и членов `openshield`;
- `/run/openshield/daemon.lock` — обычный файл `0600`, принадлежащий root,
  для блокировки единственного экземпляра;
- `/run/xtables.lock` — стандартная блокировка сериализации xtables,
  создаваемая tmpfiles с владельцем `root:root` и режимом `0600`;
- `/var/lib/openshield/state.json` — атомарно сохраняемый файл состояния
  `0600`, принадлежащий root.

Права Unix-сокета — только первая проверка. Демон также аутентифицирует
клиентов управления и наблюдения через Linux `SO_PEERCRED`, включая ограниченную проверку
стабильного членства наблюдателя в дополнительной группе. Не переносите сокеты в
общий временный каталог и не ослабляйте проверки владельца.

`ProtectSystem=strict` оставляет доступными для записи только два каталога
OpenShield и заранее созданный `/run/xtables.lock`. Исключение для одного файла
нужно, потому что старые и новые реализации xtables по умолчанию используют
эту общую блокировку; частная блокировка нарушила бы сериализацию с другими
процессами xtables. Демон очищает окружение дочерних процессов фаервола, поэтому
переопределение `XTABLES_LOCKFILE` на уровне сервиса намеренно не входит в этот контракт.
Правила tmpfiles изменяют и перемаркировывают только два точных каталога и точный путь блокировки,
не обходя их содержимое. Они не обнуляют существующую блокировку и не дают группе право записи.
Пакет должен применить декларацию до первого ручного старта; при загрузке unit упорядочен после
и требует `systemd-tmpfiles-setup.service`.

## Граница старта и остановки

`ExecStartPre` вызывает фиксированную доступную только root команду
`openshield-daemon --install-fail-closed`. Долгоживущий демон повторяет установку
карантина `BlockAll` в ядре до чтения или активации политики. При первой установке
он сохраняет `Learning`; уже сохранённый режим не меняется. Сохранённая политика
активируется только после проверки и запуска обоих фиксированных обработчиков
NFQUEUE: закрытой при отказе очереди 1337 для Enforcing и прикладных запретов
Learning, а также немедленной наблюдательной очереди Learning 1338.

Основной процесс использует `Type=notify` и отправляет `READY=1` только после
активации политики, обоих обработчиков NFQUEUE и проверенных IPC-сокетов. `ExecStopPost`
устанавливает в ядре `BlockAll` после освобождения основным процессом блокировки
единственного экземпляра. При штатной остановке сам демон также устанавливает этот карантин,
не меняя сохранённый режим.

Unit-файл задаёт `Before=network-pre.target`, а после включения его ссылка
`RequiredBy=network-pre.target` заставляет штатных потребителей зависеть от успешной
готовности. Простая установка unit-файла такую ссылку не создаёт. Сетевой менеджер,
компонент initramfs, unit-файл или ранний тракт пакетов, обходящий
`network-pre.target`, обходит и это упорядочивание. Строгая фильтрация на всём этапе загрузки
требует отдельной проверки в дистрибутиве или политики initramfs.

`Restart=on-failure` повторяет предварительную установку закрытого при отказе режима.
Не удаляйте `daemon.lock`: каждая операция открывает его с `O_NOFOLLOW|O_CLOEXEC`,
проверяет метаданные и блокирует тот же постоянный inode до изменения состояния или
фаервола.

## Полномочия и укрепление

Сервис работает с UID 0 и основной группой `root`, а также явно добавляет
дополнительную группу `openshield`. Как владелец сокета демон может назначить ему эту дополнительную
группу без `CAP_CHOWN`. Сочетание `Group=root` с нерекурсивными правилами tmpfiles не
позволяет systemd менять сохранённые runtime-блокировки или постоянное состояние перед запуском. Сервис сохраняет
`CAP_NET_ADMIN`, `CAP_NET_RAW`, `CAP_SYS_PTRACE` и `CAP_DAC_READ_SEARCH`. Legacy xtables требует `CAP_NET_RAW` для открытия raw-сокетов
IPv4/IPv6 при проверке альтернативного бэкенда и работе резервного бэкенда.
Два последних полномочия нужны, чтобы связать inode поставленного в очередь сокета с защищёнными
метаданными `/proc/<pid>` для процессов разных локальных
UID. Фильтр системных вызовов запрещает прямые вызовы исследования, включая `ptrace`,
`process_vm_*`, `kcmp`, `pidfd_getfd` и `open_by_handle_at`.

Динамически пересчитываемые имена L3 `KernelNative`, L2 `ConntrackHybrid` и L1 `Nfqueue` из
`StatusV2` классифицируют активный тракт политики. Это не уровни возможностей ядра и не
резервные реализации неизменной политики. Единственный автоматический резервный переход бэкенда при
старте выполняется с nftables на полный набор iptables/ip6tables. Эти классификации не загружают eBPF.
Пакет OpenShield намеренно не добавляет ни `CAP_BPF`, ни модуль ядра,
изменение параметров загрузки или регистрацию MOK.

Для быстрого пользовательского тракта, добавленного в v0.1.32, не нужны дополнительные
полномочия: в одну операцию входят не более 32 уже готовых пакетов NFQUEUE, при
этом сохраняются отдельный `SOCK_DIAG` для каждого пакета, ограниченные снимки
владельцев procfs до и после захвата, согласованность обязательной идентичности и
единый 250-миллисекундный срок с закрытием при отказе. Наблюдение таблиц, цепочек
и счётчиков nftables выполняется одним фиксированным процессом в секунду с теми
же проверками целостности. Изменять пакеты, LSM, Secure Boot или конфигурацию
модулей ядра не требуется.

Это сокращение поверхности атаки, а не полная изоляция. После компрометации демона
сохранённые полномочия всё ещё могут открыть доступ к памяти процесса и файлам через другие
системные вызовы или магические ссылки procfs. Перед развёртыванием изучите
[модель угроз](../../docs/THREAT_MODEL.ru.md).

## SELinux и AppArmor

Пакет не задаёт `SELinuxContext=` или `AppArmorProfile=` и не отключает ни один LSM. tmpfiles
создаёт runtime-каталог, каталог состояния и общую блокировку xtables с владельцем `root:root`, затем
восстанавливает для этих трёх точных путей контексты из установленной базы контекстов SELinux.
Нерекурсивные правила `z` не перемаркировывают их содержимое.

Это обеспечивает совместимость со штатной политикой дистрибутива, но не является встроенной
политикой изоляции OpenShield. Локальный домен SELinux или профиль AppArmor должен явно разрешать
задокументированные файлы демона, атрибуцию через procfs, семейства сокетов, полномочия и запуск
фиксированных исполняемых файлов nftables/xtables. Диагностируйте отказы, не отключая enforcing-режим:

```console
systemctl show openshield-daemon.service -p Group -p SupplementaryGroups
ls -ldZ /run/openshield /var/lib/openshield /run/xtables.lock
sudo ausearch -m AVC,USER_AVC -ts boot
sudo journalctl -k -b --grep='apparmor="DENIED"'
```

В SELinux-системах `matchpathcon -V` сравнивает существующий путь с политикой; `restorecon -v` для трёх
точных путей выше безопасно повторно применяет контексты из политики. Не обходите отказ через
`setenforce 0`, `aa-complain`, широкое разрешающее правило или непроверенный результат `audit2allow`.

## Эксплуатационное предупреждение

Свежее состояние имеет режим `Learning`, но входящий трафик по умолчанию запрещён во
всех режимах. Первое включение может прервать единственную SSH- или VPN-сессию.
Используйте локальную консоль или независимый внеполосный канал, создайте узкое
входящее правило для администрирования, проверьте вторую сессию, просмотрите изученные
исходящие правила и только затем переходите в `Enforcing`. `Learning` разрешает
несовпавший локально созданный исходящий трафик, сохраняя действие включённых
явных `drop`/`reject`; успешно атрибутированные конечные точки становятся включёнными
правилами `accept`. Для каждой группы приложения также создаётся один отключённый
шаблон с путём и, при наличии, cgroup. Его включение доступно только root и в
этот момент закрепляет версию исполняемого файла. Отключение неизменённого
шаблона возвращает канонический каркас без привязки, поэтому каждое последующее
включение заново привязывает актуальный файл; изменённый неминимальный шаблон
сохраняет полную спецификацию и привязку в отключённом состоянии. В обоих
обычных режимах включённые исходящие правила применяют `accept`, `drop` или
`reject`, а `enabled: false` делает любое правило неактивным. Разрешение по
умолчанию в `Learning` не отменяет включённый явный запрет. Входящие
правила остаются только разрешающими.

Не запускайте другой привилегированный менеджер фаервола, пока не проверены
порядок цепочек, два старших бита пакетной метки и младшие 31 бит метки conntrack,
зарезервированные OpenShield. Бит 31 conntrack сохраняется. Мониторинг OpenShield
не доказывает безопасность произвольных одновременных изменений набора правил.
