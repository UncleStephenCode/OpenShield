# Упаковка и интеграция с системой инициализации

OpenShield содержит заготовки пакетов для systemd, OpenRC, SysVinit,
runit, s6 и dinit. Все они реализуют один жизненный цикл безопасности:

1. создать или проверить группу наблюдения `openshield`;
2. установить в ядре `BlockAll` до запуска долгоживущего демона;
3. запустить демон от root по фиксированному пути `/usr/bin/openshield-daemon`;
4. повторно установить в ядре `BlockAll` после остановки под управлением супервизора;
5. не менять сохранённый запрошенный режим при таком карантине.

Обычный исходный сохраняемый режим — `Learning`. Он разрешает несовпавший
локальный исходящий трафик, сохраняет действие включённых явных `drop`/`reject`,
создаёт включённые точные правила `accept` и по одному
отключённому шаблону с путём и, при наличии, cgroup на каждую наблюдаемую группу
приложения. Предстартовый карантин —
временная политика ядра, а не замена этого сохранённого режима. Новый входящий
трафик сервисов остаётся запрещённым по умолчанию; точные DHCP/IPv6-исключения
обычных режимов отсутствуют в `BlockAll`.

## Подготовка дерева пакета

Сначала соберите релизные двоичные файлы. Затем вызовите сценарий с уже
существующим корнем пакета, принадлежащим вызывающему пользователю и имеющим
безопасные права, одним поддерживаемым именем системы инициализации и абсолютным
каталогом, содержащим оба двоичных файла:

```console
packaging/stage-install.sh /absolute/package-root systemd /absolute/release-dir
```

При необходимости замените `systemd` на `openrc`, `sysvinit`, `runit`, `s6` или
`dinit`. Помощник проверяет аргументы и отклоняет `/`, компоненты `..`, символические ссылки
в лексических компонентах целевого пути, чужие по владельцу объекты, каталоги с записью для
группы/остальных и обычные файлы с несколькими жёсткими ссылками во всём дереве. Перед каждой записью он
также проверяет каноническую цепочку родительских каталогов и допускает только безопасные каталоги,
принадлежащие вызывающему или системе; единственное исключение — системный sticky-каталог `/tmp`. Проверки завершаются
на первом отклоняемом объекте. Помощник не включает сервис и не запускает его на хосте. Он размещает:

- оба двоичных файла в `/usr/bin`;
- лицензию в `/usr/share/openshield`;
- помощник создания группы в `/usr/libexec/openshield`;
- декларации sysusers и tmpfiles для systemd или файлы выбранного не-systemd сервиса в обычных
  каталогах.

Вызывающий сценарий считается доверенным и не должен одновременно менять уже проверенное дерево.
Используйте свежий закрытый корень пакета и не давайте другим процессам право записи во время подготовки:
помощник не защищает дерево от гонки, созданной его же злонамеренным владельцем.

Передайте это дерево пакетному менеджеру целевого дистрибутива. Сценарий
сопровождения пакета должен создать группу до первого старта. Пакет systemd должен вызвать sysusers и tmpfiles
до первого ручного старта, чтобы существовал стандартный `/run/xtables.lock` с владельцем root и режимом `0600`.
Другой пакет может от root вызвать фиксированный идемпотентный
помощник `/usr/libexec/openshield/ensure-group`.

Не запускайте сервис автоматически при неконтролируемом удалённом обновлении, если
входящее правило администрирования и независимый путь восстановления не проверены заранее.
Входящий трафик запрещён по умолчанию даже в `Learning`.

Совместимость состояния и IPC односторонняя: от v0.2.0 к v0.2.1. Версия v0.2.1
трактует отсутствующее действие правила как `accept`, но v0.2.0 не читает
действия `drop`/`reject` и источник `template` из v0.2.1. Не запускайте смешанные
версии демона и TUI и не понижайте версию на месте после записи состояния
v0.2.1. Обновление и откат выполняйте из защищённой консоли, при активном в ядре
`BlockAll`, с проверенной резервной копией состояния и испытанной для
дистрибутива процедурой.

## Локальная конфигурация квот обучения

При запуске демон может читать `/etc/openshield/learning-limits.json`.
Файлом управляет администратор; он не входит в пакет, поэтому установка и
обновление не должны создавать или перезаписывать его. При отсутствии файла
v0.2.8 использует `{"per_uid":4096,"per_application":1024}`. Root может задать
оба целочисленных поля в пределах `1 <= per_application <= per_uid <= 7500`.
Родительские каталоги должны принадлежать root, не быть символическими ссылками
и не допускать запись группой или остальными; сам файл должен быть обычным,
принадлежать root и иметь режим `0600`. Демон читает его после установки
начального `BlockAll`; некорректная или небезопасная конфигурация прерывает
запуск. После проверки изменений перезапустите демон из защищённой консоли.
Существующее состояние сохраняется, но ранее пропущенные конечные точки
нужно повторно наблюдать в Learning.
См. [описание квот](../README.ru.md#квоты-обучения-в-v025).

## Матрица релизных пакетов

Авторитетный релизный workflow собирает 43 двоичных артефакта для пар
архитектура/семейство и 43 соответствующих пакета. Его подматрица времени
выполнения охватывает 19 вариантов пакетов в 37 закреплённых строках
дистрибутив/OCI-платформа: 16 для `amd64`, 15 для `arm64` и 6 для `386`.
Свидетельства установки остаются независимыми для каждой выбранной версии и
платформы. Каждая строка проходит сценарии Learning-to-Enforcing для nftables и
iptables — всего 74 задания фаервола, которые должны завершиться до публикации. Это
условия workflow, а не утверждение, что новая матрица уже прошла все задания.

Нативные исполнители запускают `amd64` и `arm64`; `386` использует прямой
32-разрядный режим совместимости ядра x86-64. Оставшиеся 24 варианта пакетов для
ARMv5/6/7, PowerPC64LE, RISC-V 64 и IBM Z соответствуют 49 из 86 объявленных пар
дистрибутив/платформа и имеют статус «только сборка». Их закреплённый тракт Cross/QEMU
проверяет ELF и выполняет smoke-тест `--version` в целевом образе, но не даёт
свидетельства установки пакета, работы фаервола или нативного оборудования. Точная
матрица и границы свидетельств описаны в [руководстве по релизному CI](../.github/README-CI.ru.md).

## Замечания по системам инициализации

| Система | Файл сервиса в дереве | Упорядочивание и надзор |
| --- | --- | --- |
| systemd | `/usr/lib/systemd/system/openshield-daemon.service` | `Type=notify`, до и с зависимостью от включённой `network-pre.target`, перезапуск при отказе, карантин до старта и после остановки |
| OpenRC | `/etc/init.d/openshield` | требует локальные файловые системы, упорядочен до `net`, надзор за фоновым PID, карантин до и после |
| SysVinit | `/etc/init.d/openshield` | метаданные LSB, `start-stop-daemon`, проверка PID/исполняемого файла, карантин вокруг жизненного цикла |
| runit | `/etc/sv/openshield/` | работающий на переднем плане `run`, проверка готовности `check`, карантин `finish` |
| s6 | `/etc/s6/sv/openshield/` | `longrun`, зависимость от файловых систем, работающий на переднем плане `run`, карантин `finish` |
| dinit | `/etc/dinit.d/openshield*` | зависимость от предварительного сценария, надзор за процессом, задержка перезапуска, карантин при остановке |

Пути и команды включения сервиса различаются между дистрибутивами. Пакет должен
использовать штатную политику preset/enable целевой системы, а не создавать непроверенную
универсальную символическую ссылку. Ни один из этих файлов не управляет initramfs или сетевым
трактом, который игнорирует объявленный порядок системы инициализации.

Демону нужен эффективный UID 0. В systemd его основной группой остаётся
`root`; `openshield` добавляется только как дополнительная группа, чтобы демон мог
назначить её собственному сокету наблюдения без `CAP_CHOWN`. Эта группа авторизует
мониторинг только для чтения и не является основной группой процесса.

## Проверка

Статическая проверка дерева пакета, режимов файлов, синтаксиса, зависимостей и
отклонения символических ссылок:

```console
scripts/test-init-matrix.sh validate
```

Контейнерные стенды парсеров и супервизоров:

```console
scripts/test-init-matrix.sh manifests
scripts/test-init-matrix.sh containers-clean
```

Контейнерный стенд проверяет разбор OpenRC, семантику `start-stop-daemon` в SysVinit,
жизненный цикл и карантинные обработчики runit и s6, разбор описания dinit и работу
помощника группы. Alpine/BusyBox также реально запускает подготовку изолированного дерева; заготовки с
небезопасными владельцами, режимами и ссылками должны быть отклонены. systemd проверяется статически при подготовке дерева и отдельно через
`systemd-analyze`; полная декларация создания и перемаркировки tmpfiles также прошла повторное применение и проверку точных
метаданных в закреплённом Tumbleweed. Стенд не загружает systemd в контейнере. Демон в стенде заменён заглушкой,
поэтому проверка не затрагивает реальный фаервол ядра, NFQUEUE, последовательность загрузки или
восстановление супервизором после ошибки фаервола.

Реальный сквозной сценарий фаервола запускайте только в его изолированной одноразовой
сети Docker, как описано в [руководстве по совместимости](../tests/compat/README.ru.md).

Особенности полномочий и готовности systemd описаны в
[daemon/README.ru.md](daemon/README.ru.md).
